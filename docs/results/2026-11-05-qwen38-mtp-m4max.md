# MTP drafts on the M4 Max: the same text, up to 37% faster (2026-11-05)

**Result.** On the M4 Max, the P3 pack gives the same greedy text with 0 to 3 MTP drafts, so gate MB passes. Drafts
make decode faster at every count. On code, 2 drafts decode at 56.0 tokens per second, against 40.9 without drafts
(+37%). On chat, 1 draft decodes at 50.6 against 42.0 (+20%). After a 20,131-token prompt, 2 drafts decode at 42.6
against 36.8 (+16%). Gate MC, as the plan states it for the 4080, passes on Metal at 1, 2 and 3 drafts. mlx-vlm 0.7.12's
own MTP reached 51.8 (code) and 43.1 (chat) at 2 drafts in mac-metal's study.

**Status.** Replaced for the speed numbers by [MTP drafts on the M4 Max, again](2026-11-05-qwen38-mtp-m4max-rerun.md). Plan step M4 of [MTP drafts](../plans/2026-11-04-qwen38-mtp.md).

## Setup

- Machine: mac-metal's Mac. Apple M4 Max (16 CPU cores, 40 GPU cores), 128 GB unified memory, macOS 27.2. No other GPU
  jobs ran during the timed runs. The P3 pack was in the page cache (a warm-up run first).
- Commit: `mac/qwen4-mtp` on `3f570f3`. The Metal engine maps every weight, the experts included, so there is no
  expert cache.
- Model: [Qwen3.8-Flash-Next-NanoSeedLM-P3](https://huggingface.co/txgsync/Qwen3.8-Flash-Next-NanoSeedLM-P3), with its
  54 `mtp.*` tensors. Its routed experts are P = 3 seeds. Every dense matrix, the head included, is affine Q4 with group 32.
- Two rounds. In each round, code then chat, and K = 0, 1, 2 and 3 in that order.

```bash
nslm-qwen4-gen --model P3 --prompt "Write a Python function that merges two sorted lists, with a docstring." --max-tokens 256 --drafts K
nslm-qwen4-gen --model P3 --prompt "Why do tide pools matter? Answer in three sentences." --max-tokens 256 --drafts K
```

## Notes

- A step of T rows takes about 12 ms + 11.8 ms x T on both prompts (a least-squares line through the means). So the
  rows share about half of a one-row step; on the 4080 they share about 30%. The Mac has no expert copies: each row
  pays its expert matvecs, and part of its dense matvecs.
- Where the time goes (`Q4E_PROFILE=2`, code, GPU ms a step; the profile runs a command buffer per stage):

  | Stage | No drafts | 2 drafts |
  |---|---|---|
  | Experts | 7.8 | 19.0 |
  | Gated DeltaNet | 5.6 | 9.3 |
  | Hyper-connections | 3.8 | 5.5 |
  | Attention: projections, attend, QSA | 3.0 | 4.7 |
  | Router | 1.0 | 1.1 |
  | Head (the main head and the drafts' heads) | 0.8 | 3.2 |
  | All | 22.1 | 43.2 |

  The experts are now the largest cost a row: 6.4 ms for each verify row past the first. The rows of one verify share
  experts (6.49 to 8.01 distinct a token in a window of 2 to 4, of 10), so a pass that reads each distinct expert once
  for all its rows is the next step. It must keep each row's sums in the order of a one-row forward.
- Gate MB holds by construction, not by luck. A forward of 2 to 4 rows gives the logits of as many one-row forwards bit
  for bit, checked on P3 after 20 to 2,400 tokens and at 510 to 770 keys. Three things make that so:
  1. The matvecs run without fast math, so a token's row sums in the same order for any row count.
  2. Each decode row's attention kernel and key splits follow from its own keys, not from the longest row of its
     forward. Before this, 4 rows that straddled 512 keys or a 128-key split boundary changed about 240,000 logits a row.
  3. The verify rows write the recurrent state (DeltaNet conv and state, the PLE conv history) after each row to
     snapshot buffers. `q4e_accept` swaps the kept row's buffers in, so a failed draft costs no copy.
- The multi-row Q4 matvec got 20 to 35% faster during this step (`log.md`, 2026-11-05). Before that, the same runs gave
  50.1, 52.2 and 50.6 tokens per second on code, and 47.4, 43.8 and 39.7 on chat.
- The drafts' share accepted is the same as in the mlx-vlm study's code runs (88% and 82% at 1 and 2 drafts, against
  94.5% and 90.3% there), and lower on chat (75% against 79%). The prompts differ.
