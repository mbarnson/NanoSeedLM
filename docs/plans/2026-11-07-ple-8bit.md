# Plan: an 8-bit PLE table in each pack (2026-11-07)

**Goal.** Each Qwen3.8-Flash-Next pack (TCQ4, TCQ3-D4, TCQ3, P4, P3) carries an 8-bit PLE n-gram table. Then every
runtime uses 8 bits: the engines, mlx-vlm and oMLX. Matt's words: "The use of a 4-bit PLE works against my quality aims."

**Status.** In progress, for v0.1.1, which waits for it (Matt). P1 is done. On the tiny fixture, `ns_row_f32` reads the
8-bit rows that `tools/hf_ple8.py` writes as MLX's `dequantize` gives them, with no difference.

## Why

- Each pack carries the 4-bit MLX table of mlx-community's 4-bit model: 32.0 GB, group 32. mlx-vlm and oMLX use it.
  It adds 0.006 of KL against Unsloth's Q8_0 table ([the PLE table page](../results/2026-11-06-ple-table-kld.md)).
- The engines use Unsloth's Q8_0 table by default, which the start scripts download as well: 54.4 GB more.
- After this plan, each pack carries one 8-bit table, and one download serves every runtime.

## The table

- From BF16: `Qwen/Qwen3.8-Flash-Next`, `model.language_model.layers.1.ple.ple_embedding.ngram_embedding.shard_N.weight`,
  128 tensors of 2,500,012 rows by 160 values (about 102 GB).
- MLX's 8-bit affine form, group 32 (64 does not divide 160), with BF16 scales and biases: 57.6 GB. The codes are taken
  against the stored BF16 scale and bias, not by `mx.quantize` (gate PA).
- The packs' names: `language_model.model.layers.1.ple.ple_embedding.ngram_embedding.shards.N.{weight,scales,biases}`.
  `config.json` gives each of the 128 modules `{"group_size": 32, "bits": 8}`. The shapes alone read as 4-bit group 64,
  so the engines take the bits from that entry (P1).
- Each tensor aligned for its type (`tools/st_pad.py`).

## Steps and gates

| Step | Work | Who | Gate |
|---|---|---|---|
| P1 | `ns_open` takes an affine tensor's bits and group from `config.json` (`6e13dd6`). The engines read the rows through `ns_row_f32`, which takes any group size | cloud | done |
| P2 | `tools/hf_ple8.py table`: the 8-bit table from BF16, in an HF job (cpu-upgrade, $0.03/h) that writes to the bucket | pc-cuda runs it | PA (passed) |
| P3 | `tools/hf_ple8.py pack`: on each pack, a pull request (not merged). It deletes the 6 files that hold only the 4-bit table, rewrites the 2 that hold some of it, and adds the 33 files of the 8-bit table, the index and `config.json`. Xet sends the table's chunks once | the same job | PB |
| P4 | Merge the five pull requests | Matt | PB, PC |
| P5 | The engine's KL between the pack's table and Unsloth's Q8_0 table, on TCQ3 at its pull request | pc-cuda | PC |
| P6 | Start scripts: the pack's own table, no Unsloth download, the new revisions pinned. Cards: the table, the download sizes | cloud | v0.1.1 |

- **PA.** On 10,000 random rows, the RMS error of the 8-bit table against BF16 is at most that of Unsloth's Q8_0 table.
  Passed: 0.88 times Q8_0's error, with codes against the stored BF16 scale and bias
  ([the encoding page](../results/2026-11-07-ple8-encoding.md)). `mx.quantize` fails it (1.19 times).
- **PB.** At each pull request, mlx-vlm and oMLX load TCQ4 and P3 and answer the stock prompts. nslm-chat on TCQ4 reads
  the pack's own table, with no `Q4E_PLE_GGUF`, and answers them too.
- **PC.** `nslm-qwen4-kld --ref-ple-gguf` (the reference run with Unsloth's table, the model run with the pack's) on
  1,024 tokens gives a KL below 0.002. For scale, the same run with the old 4-bit table.

## Costs

- Each pack grows by 25.6 GB: TCQ4 to 127.5 GB, TCQ3-D4 117.2, TCQ3 112.1, P4 131.3, P3 123.8. The engines' downloads
  shrink by 28.8 GB, since the Q8_0 table is no longer needed.
- RAM does not change: the table stays on the disk, and the page cache holds the rows that a session reads. An 8-bit row
  is 180 bytes, as against 170 for Q8_0 and 100 for the 4-bit table.
- No HF jobs. A KL in llama.cpp with the new table can follow when the weekly budget resets.
